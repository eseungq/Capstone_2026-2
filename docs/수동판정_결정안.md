# AI 무응답 시 수동 판정 결정안 (팀 결정용)

> **11/11 B안으로 구현·실서버 시험 완료** (V6, `POST /inspections/{id}/manual`, 통합 테스트 6건, 계약 v4 6.10, 앱 PR #18, 점검표 M1 통과: INS-000116 → 117). 김남균 V6 확인 남음

작성: 이승규 · 11/10 · 근거: 교수님 피드백 "AI 무응답 시 수동 판정 보강", 통합 점검표 M1

## 1. 지금 상태

- AI가 응답하지 않으면(연결 실패·5xx·시간 초과·응답 오류) 검사는 **FAILED**가 되고, 할 수 있는 일은 **재검사(retry)** 뿐입니다.
- AI 서버가 계속 멈춰 있으면 재검사도 계속 실패해서, 그 부품은 **최종 판정 없이 남습니다.** 현장에서는 라인을 멈추거나 시스템 밖에서 기록해야 합니다.
- DB 제약(V5 `chk_insp_failed_v5`)이 FAILED 검사에 판정 값(`judged_by`)을 넣지 못하게 막고 있어, 어떤 방식이든 **V6 마이그레이션**이 필요합니다.

## 2. 선택지

| | A. FAILED 건에 바로 수동 판정 | B. 수동 판정용 검사를 새로 만듦 | C. 절차만 정하고 기능은 없음 |
|---|---|---|---|
| 흐름 | FAILED 상세에서 작업자가 원본 사진을 보고 PASS/FAIL 입력 | FAILED 상세에서 "수동 판정으로 전환" → 원본을 재사용한 새 검사(출처 MANUAL)가 생기고, 기존 확인 흐름으로 판정 | 재검사를 반복하고, 계속 실패하면 현장 육안 검사 결과를 시스템 밖에 기록 |
| 기록 | 검사 1건에 오류 코드와 수동 판정이 함께 남음 | FAILED 원본은 그대로, 새 검사에 판정. 재검사(RETRY)와 같은 구조 | 시스템에 최종 판정 없음 |

| 이력·목록 | 새 표시 상태 필요 (예: 수동 판정 완료) | 새 검사는 REVIEW 흐름 그대로, 사유만 추가 (예: `AI_UNAVAILABLE`) | — |
| DB 변경 | FAILED 규칙 완화 (판정 허용) | COMPLETED 규칙 완화 (AI 점수·Grad-CAM 없는 검사 허용), 출처·사유 값 추가 | 없음 |
| 작업량 (백엔드) | 0.5~1일 | 1~1.5일 | 0 |
| 작업량 (앱) | 0.5일 | 0.5~1일 | 0 |
| 장점 | 가장 단순, 기존 확인 API 재사용 | "AI 실패 기록은 바꾸지 않는다"는 지금 원칙 유지, 재검사와 구조가 같아 설명하기 쉬움 | 구현 없음 |
| 단점 | FAILED의 의미가 "실패, 이후 수동 확정 가능"으로 넓어짐 | 작업량이 조금 더 많음 | 교수님 피드백에 답이 안 됨 |

## 3. 추천: B

- 지금 설계는 **FAILED 기록을 바꾸지 않고**(재검사도 새 검사로 생성) 감사 추적을 남기는 원칙입니다. B는 이 원칙을 그대로 지키고 재검사와 같은 모양이라 보고서·시연에서 설명이 쉽습니다.
- 앱은 이미 REVIEW 상세에 판정 화면이 있어서, 새 검사로 이동만 시키면 판정 화면은 그대로 씁니다.
- 일정이 빠듯하면 A도 충분합니다. C는 피드백 대응으로 부족해 추천하지 않습니다.

## 4. 정해야 할 것

1. A·B·C 중 무엇으로 할지
2. **언제 수동 판정을 허용할지**: FAILED 즉시 / 재검사 1회 실패 후 / 특정 오류(AI 연결 실패·시간 초과)만
3. **누가**: WORKER만 (지금 확인 권한과 같음) 또는 ADMIN 포함
4. **화면 문구**: "AI 분석 없이 작업자 판정" 같은 표시를 이력·상세에 어떻게 보일지
5. **사유 입력**: 수동 판정 시 메모(사유)를 필수로 받을지 (지금 확인은 선택 200자)

## 6. 세부 설계안 (11/11, 구현 기준)

**흐름**: FAILED 상세 → `POST /api/v1/inspections/{id}/manual` → 새 검사(출처 `MANUAL`, 확인 필요) 상세로 이동 → 기존 `POST /inspections/{newId}/confirm`으로 PASS/FAIL (2단계, 판정 화면 재사용)

| 항목 | 설계 |
|---|---|
| 허용 조건 | 원본 검사 `status=FAILED`, 아직 재검사·수동 전환이 없음, 원본 이미지 기록 있음. **AI 모델 확인 안 함** (재검사와 다른 점) |
| 재검사와 하나만 | 수동 건도 재검사와 같은 `retry_of_inspection_id`(원본 FAILED 연결, UNIQUE)를 씀 → 한 FAILED에 후속 검사 1건만, 동시 요청도 DB가 하나만 남김. 이미 있으면 재검사·수동 모두 409 `ALREADY_RETRIED` (문구: "이미 재검사 또는 수동 판정으로 전환된 검사입니다") |
| 새 검사 값 | `status=COMPLETED`, `source=MANUAL`, `recommended_action=REVIEW`, `review_reason=AI_UNAVAILABLE`, 예측·점수·보정·CAM·정책 모두 null, 사진은 원본 파일 재사용(재검사와 같음), 모델은 원본 FAILED의 모델 그대로(`model_id` 필수 칸, 어떤 모델이 실패했는지 기록) |
| 판정 기록 | 기존 confirm 그대로 → `final_judgement`·`judged_by=WORKER`·판정 시각·메모(선택 200자). 새 검사 상세에 **원본 FAILED의 번호·오류 코드**를 함께 보여 AI 실패 사유와 최종 판정을 한 화면에서 확인 |
| 표시 | `reviewReason=AI_UNAVAILABLE` → 앱 "AI 분석 없이 작업자 판정". 상세·이력 응답에 `source` 추가 |
| 권한 | 전환 WORKER (ADMIN·DEVICE 403). 판정은 기존과 같음 |
| 집계 | 후속 검사가 있는 FAILED는 지금처럼 실패 건수에서 빠짐. 수동 건은 판정 전까지 확인 필요 건수에 포함 |
| 판정할 수 없는 사진 | 원본 누락·손상·다른 부품이면 작업자가 전환하지 않고 재촬영·재접수 (앱 안내 문구). 원본 기록이 없으면 서버가 거절 |

**V6 마이그레이션 (김남균 확인)**
- `source` 허용값에 `MANUAL`, `review_reason` 허용값에 `AI_UNAVAILABLE` 추가
- 완료 검사 규칙(`chk_insp_completed_v5`): `MANUAL`이면 보정 전 점수·CAM 상태 없어도 됨
- 새 규칙: `MANUAL` ⇔ `review_reason=AI_UNAVAILABLE`, 예측·점수·정책 없음, `recommended_action=REVIEW`, 원본 연결 필수
- 무결성 점검 추가: 수동 건의 원본이 FAILED인지, 원본과 같은 사진 파일인지

**알려진 한계**: AI가 응답은 하지만 모델이 없다고 하면(`NOT_LOADABLE`) 접수 자체가 422라 검사 기록이 없음 → 수동 판정 불가, 재접수 필요. AI가 아예 응답하지 않으면 접수 후 FAILED가 되므로 수동 판정 가능 (교수님 피드백 "AI 무응답"은 이 경우)
